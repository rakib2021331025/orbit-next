# Authorization matrix

Generated by scanning every page in `Orbit/` for the gate it actually applies —
`require_admin()`, `student_auth.php`, `orbit_admin_require_super()` and the rest
— not from memory and not from the menus. 149 pages. `Orbit/` was not modified to
produce this.

This is the specification `lib/auth/guards.ts` implements, and the checklist for
verifying each migrated page.

---

## The rule that matters

**A user who edits the URL must gain nothing.** Every row below is enforced on
the server, before any data is read. Hiding a link is not access control: the
migrated app must refuse `/admin/students` to a student even though no student
page links to it.

Two layers do this, and the order is deliberate:

| Layer | Where | Checks | If it were removed |
|---|---|---|---|
| `middleware.ts` | edge, per request | cookie signature + role prefix | app still secure, just slower |
| `lib/auth/guards.ts` | server component / action | **the live database row** | app is insecure |

The cookie is signed, so it cannot be edited into an admin session. But it is
still only a claim: the guards re-read the account on every request, so locking
an admin, deactivating a guardian or deleting a student takes effect on that
account's next click rather than whenever its 8-hour session happens to lapse.

A role reaching another portal is not sent to a login form. It is redirected to
its own portal — a student who follows an `/admin` link should not be invited to
type admin credentials.

## Super-admin-only pages (7)

These call `orbit_admin_require_super()` on top of the admin gate. A branch admin

`admin/fees.php` · `admin/reports.php` · `admin/coaching_analytics.php` ·
`admin/inquiries.php` · `admin/monthly_exams.php` ·
`admin/monthly_exam_marks.php` · `admin/exam_results_management.php`

→ `requireSuperAdmin()`

## Developer-only pages (2)

`admin/admins.php` · `admin/branches.php`

→ `requireDeveloper()`, which reads `ORBIT_DEVELOPER_EMAIL` **from the
environment and never from `site_settings`**. An admin can edit every setting, so
a setting would let them hand the page straight back to themselves. When no
developer address is configured the pages fall back to super admins, matching
`orbit_admin_may_manage_admins()`.

## Branch scoping (21 pages)

A branch admin is pinned to one branch. Three separate rules, all of which must
carry over:

1. **Allow-list, not deny-list.** `orbit_branch_admin_allowed_scripts()` names the
   19 admin scripts a branch admin may open; everything else in `admin/` is
   refused. A page added later is therefore closed by default. `guards.ts` keeps
   the same shape — a new page must be added deliberately.
2. **List queries** narrow with `orbit_branch_where(shared: true)`: their own
   branch *plus* rows with `branch_id IS NULL`, which are shared by all branches.
   → `branchWhere(true)`
3. **Record access** is checked by id with `orbit_admin_require_record()`, which
   keeps a hard-coded table list and **refuses any table it does not recognise**
   rather than guessing. Shared rows (`branch_id IS NULL`) are readable but not
   writable by a branch admin — `shared: false` on a write.
   → `requireRecordBranch(table, id, shared)`

Pages that guard a record id today:

| Page | Tables |
|---|---|
| `media.php` | `admissions`, `assignment_submissions`, `students` |
| `admin/payment_tracking.php` | `payments`, `students` |
| `admin/class_routine_management.php` | `class_routine` |
| `admin/payment_screenshot.php` | `admissions` |
| `admin/recorded_classes.php` | `recorded_classes` |

The registered tables, from `orbit_admin_can_record()`:

- **direct `branch_id`** — `students`, `admissions`, `batches`, `notice`,
  `class_routine`, `assignments`, `study_materials`, `live_classes`,
  `recorded_classes`, `exams`, `attendance`, `payments`
- **via the student** — `exam_results`, `enrollments`, `assignment_submissions`

A branch admin with `branch_id` NULL is treated as **locked**, not as
all-branches. Otherwise their filter matches nothing, and the natural
implementation of "no filter" is "every branch".

`?branch=` is a **reserved query parameter** — it switches an admin's active
branch. A page needing its own branch filter must name it something else;
`admin/recorded_classes.php` uses `fbranch` for exactly this reason.

## Row ownership inside a portal

Being signed in as a student is not authorisation to read *a* student's data —
only their own. The ownership rules, which are the ones a URL-editing user
attacks first:

| Portal | Rule | Where it comes from |
|---|---|---|
| Student | every query filtered by the session's `student_id`; a submission, result or payment id belonging to someone else is not found | each student page |
| Guardian | `?student=<id>` is resolved **only against the guardian's own linked, active children**; any other id is a **404**, not a 403 | `guardian_auth.php` → `requireGuardianChild()` |
| Teacher | their own batches | `teacher/*.php` |
| Admin | branch lock, above | `branch_lib.php` |

A 404 rather than a 403 for another family's child is deliberate: a 403 confirms
the student exists.

## Sign-in

| Portal | Identifier | Column | Status condition |
|---|---|---|---|
| Student | username | `student_login.password` | **none** — `students.status` is deliberately not tested |
| Teacher | email | `teachers.password_hash` | `status = 'active'` |
| Guardian | phone (normalised) | `guardians.password` | `status = 'active'` |
| Admin | email | `admins.password_hash` | `status = 'active'` + a branch admin must have a branch |

The asymmetry on the student row is not an oversight to be tidied up:
`student/login.php` and `student_auth.php` both JOIN `students` without testing
`status`, so a student whose admission row is still `pending` can sign in once an
admin has created their login. Adding a filter would lock out students the PHP app
admits.

Shared by all four:

- **bcrypt**, with PHP's `$2y$` prefix rewritten to `$2a$` before comparing —
  same algorithm, different version byte. Without that rewrite every existing
  account would be refused on cutover day with a correct password.
- **Rehash on sign-in** when the stored cost is below 10, as
  `password_needs_rehash()` does.
- **Throttling** in `login_attempts`: 5 failures per identifier and 25 per IP in
  15 minutes. Identifiers are stored as a SHA-256 hash, so the table never holds
  a username. Counting both ways matters — per-identifier alone lets an attacker
  lock a real user out, per-IP alone lets them walk a list of accounts.
- **Timing equalisation**: when no account matches, the password is still
  verified against a dummy bcrypt hash, so the response time does not reveal
  which identifiers are registered.
- **The same message** whether the identifier or the password was wrong. A locked
  account is told it is locked, but only after its password verified.
- **CSRF**: the PHP forms carry `csrf_verify()`; a Next.js server action is
  rejected unless the request's Origin matches the host, which covers the same
  attack without a token in the form.

Throttled elsewhere in the original, and to keep: `check_status.php` (8/30),
`results.php` (5/25), `student/settings.php`, `guardian/settings.php`.

### First-login lock

`must_change_password` on a student or guardian blocks **every** page except
settings and logout until the temporary password issued at approval is replaced.
Enforced by `requireStudentUnlocked()` / `requireGuardianUnlocked()`; the settings
pages call the plain `requireStudent()` / `requireGuardian()` so the redirect
cannot loop.

### Remember me

`auth_remember_tokens`, 30 days, cookie `selector:validator`. Only the selector is
stored in the clear; the validator is stored as a SHA-256 hash, so a dump of the
table cannot be replayed as a login.

- comparison is **constant-time** — `===` leaks how many leading bytes matched
- a known selector with a **wrong** validator deletes **every** token the account
  has: the honest reading is that a cookie was stolen
- each successful restore **rotates** the token, so a cookie is usable once
- restoring re-checks the account: a locked admin, an inactive teacher, a
  deactivated guardian or a student no longer `Active` is not signed back in
- the remembered id for a student is **`student_login.id`**, not `students.id` —
  the original's convention, and changing it would invalidate live cookies
- **logout drops only this device's token**, so signing out on a phone leaves a
  desktop remembered. `logoutEverywhere()` exists for a password change, where
  revoking the others is the point.

### Signed links

`marksheet_share.php` takes no session at all — it accepts an HMAC token
(`orbit_sign_token()` / `orbit_verify_token()`, purpose + id + expiry) so a
marksheet can be sent over WhatsApp. The signature and the expiry are the whole
authorisation; the secret lives in `site_settings.app_secret`.

## Verification checklist

Per migrated page, in the browser and with `curl`:

1. signed out → redirected to that portal's login, not rendered
2. signed in as each **other** role → redirected to their own portal
3. `?id=` / `?student=` pointing at another user's row → 404, not their data
4. as a branch admin, a record from another branch → 403
5. as a branch admin, a page outside the allow-list → 403
6. a shared (`branch_id IS NULL`) record → readable, not writable by a branch admin
7. `must_change_password` set → every page bounces to settings
8. the session cookie edited by one byte → treated as signed out
9. 6 wrong passwords → throttled, and the 6th does not reveal whether the account exists
10. locked / deactivated while signed in → refused on the next request, not at session expiry

Items 1–3 are the ones a URL-editing user tries first, and 10 is the one an
ordinary test plan misses.
